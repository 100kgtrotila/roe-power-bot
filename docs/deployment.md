# Налаштування Telegram і хостинг на Cloudflare

Worker обробляє команди через webhook і запускає cron у Cloudflare. Комп'ютер
власника після розгортання не потрібен. Цей гайд описує дії власника: хмарні ресурси
й справжній webhook не створюються під час локальних тестів.

## 1. Створіть бота й конфігурацію

У Telegram відкрийте **@BotFather**, виконайте `/newbot`, задайте назву й username.
Збережіть отриманий токен. Розкритий токен відкличте через BotFather.

Встановіть Node.js 22.12+ (підтримуваний LTS) та pnpm 10.33.0. У PowerShell:

```powershell
cd D:\Projects\roe-power-bot
pnpm install --frozen-lockfile
Copy-Item .dev.vars.example .dev.vars
```

Копіюйте приклад лише коли `.dev.vars` ще немає. Відкрийте файл у редакторі:

```dotenv
BOT_TOKEN=токен_від_BotFather
WEBHOOK_SECRET=власний_випадковий_секрет
ALLOWED_TELEGRAM_IDS=
```

Згенеруйте окремий секрет, який не є токеном Telegram:

```powershell
node --input-type=module -e "import { randomBytes } from 'node:crypto'; console.log(randomBytes(32).toString('hex'))"
```

Скопіюйте результат у `WEBHOOK_SECRET`. Файл `.dev.vars` ігнорується Git.
Не вставляйте токен у командний рядок, посилання, скриншоти або README.

## 2. Дізнайтеся свій Telegram ID

До реєстрації webhook відкрийте свого бота, надішліть `/start` і виконайте:

```powershell
pnpm run telegram:webhook -- id
```

Скрипт читає токен із `.dev.vars`, перевіряє відсутність webhook, викликає
`getUpdates` і друкує лише ID приватних відправників. Тексти та сирі updates
не друкуються. Оберіть свій ID; у нового приватного бота зазвичай він один.
Якщо список порожній, надішліть `/start` і повторіть.

`getUpdates` не працює одночасно з активним webhook. Скрипт відмовиться запускати
його в такому разі; для вже налаштованого бота використайте збережений ID.

У `.dev.vars` заповніть `ALLOWED_TELEGRAM_IDS=123456789`. Кілька ID перелічіть
через кому. Порожній чи некоректний список забороняє доступ усім. Потрібен саме
числовий ID користувача, а не username, телефон або ID групи.

У `wrangler.jsonc` також задайте список у `vars.ALLOWED_TELEGRAM_IDS` — це
конфігурація хмарного Worker; `.dev.vars` під час deploy не публікується.

## 3. Перевірте локальний запуск

```powershell
pnpm run db:migrate:local
pnpm test
pnpm run typecheck
pnpm run lint
pnpm run build
pnpm dev
```

Перевірте `http://localhost:8787/health`: очікується `{"status":"ok"}`.
Зупиніть dev через Ctrl+C. Endpoint перевіряє лише HTTP-процес, а не Telegram,
D1 чи публікацію графіків. Telegram не доставляє webhook на localhost.

## 4. Увійдіть у Cloudflare й створіть D1

Зареєструйте акаунт Cloudflare, потім:

```powershell
pnpm exec wrangler login
pnpm exec wrangler d1 create roe-power-bot
```

У `wrangler.jsonc` замініть `database_name` на `roe-power-bot`, а нульовий
`database_id` — на UUID з відповіді. Залиште `binding: "DB"` і
`migrations_dir: "migrations"`. Не додавайте другу копію binding.

```powershell
pnpm exec wrangler d1 migrations apply DB --remote
```

`--local` і `--remote` — різні бази. Наявність локальних таблиць не означає,
що вони є в хмарі. Застосовані міграції не редагуйте.

## 5. Опублікуйте Worker і додайте секрети

```powershell
pnpm run deploy
pnpm exec wrangler secret put BOT_TOKEN
pnpm exec wrangler secret put WEBHOOK_SECRET
```

Wrangler запитає значення інтерактивно. Вставте ті самі значення, що у `.dev.vars`.
Перший deploy без секретів можливий: без токена cron ще не працює, webhook
повертає 503. Секрети не записуйте у `wrangler.jsonc`. Збережіть HTTPS-адресу
`*.workers.dev` із виводу deploy.

Список `ALLOWED_TELEGRAM_IDS` має бути заданий у `wrangler.jsonc` перед deploy.
Щоб змінити список, відредагуйте конфігурацію та повторіть deploy.

## 6. Підключіть Telegram

Підставте свою адресу замість прикладу:

```powershell
pnpm run telegram:webhook -- set https://roe-power-bot.YOUR-SUBDOMAIN.workers.dev
pnpm run telegram:webhook -- info
```

Скрипт додає `/webhook`, передає `secret_token` та дозволяє лише `message` і
`callback_query`. Повторний `set` оновлює адресу й секрет без видалення pending updates.

`info` показує `configured`, `pendingUpdateCount`, `hasDeliveryError`, без секретів.
Історична помилка може залишатися після виправлення: перевірте нову команду й
зменшення pending. Саме `configured: true` ще не підтверджує працездатність.

За бажанням у BotFather через `/setcommands` задайте:

```text
start - Головне меню
queue - Обрати підчергу
schedule - Мій графік
all - Усі черги
reminders - Налаштувати нагадування
status - Стан перевірок сайту
stop - Керування сповіщеннями
help - Допомога
```

## 7. Перевірте справжню роботу

1. Надішліть `/start` у приватному чаті. У постійному меню внизу натисніть
   «Моя підчерга» та оберіть підчергу або всі кнопками під повідомленням.
2. Бот покаже збережений графік. На першому запуску кеш може бути порожнім:
   дочекайтеся cron і повторіть `/schedule`. Поширення змін Cron Triggers у
   Cloudflare може тривати до 15 хвилин.
3. Перевірте `/all`: власний вибір не повинен змінитися.
4. За потреби увімкніть нагадування кнопкою й оберіть 15/30/60 хвилин.
5. `/stop` відкриває меню. Для паузи натисніть «Вимкнути все» або вимкніть
   потрібний вид повідомлень. Ручний перегляд залишається доступним.

Команди можна замінити кнопками постійного меню. «Стан перевірок» (або `/status`)
показує, чи була спроба прочитати сайт, коли востаннє вдалося розібрати дані та
коли очікується наступна спроба. Це збережені дані, а не примусовий запит до сайту.
Якщо перевірка прострочена, бот попереджає про затримку; відповідь на команду
сама по собі не є підтвердженням роботи cron. Для повернення з налаштувань є
«Головне меню». Якщо клавіатура прихована, відкрийте її значком біля поля введення.

Початкове «Очікується» не створює автоматичних повідомлень. Новий графік
надходить після найближчої успішної перевірки, зазвичай приблизно за 0–5 хвилин
плюс доставка. Незмінний графік кожні 5 хвилин не надсилається. Нагадування
працюють цілодобово. Пізно опублікований графік поєднується з відліком до
близького початку без окремого негайного дубля нагадування.

Парсер підтримує «Очікується» й формат опублікованого графіка, зафіксований
24.11.2026. У рядку з опублікованими годинами порожня клітинка означає
відсутність відключень для відповідної підчерги. Порожні клітинки в рядку
без жодного інтервалу або невідомі значення спричиняють помилку парсингу.
У разі помилки бот зберігає останні коректні дані.

## 8. Діагностика й ліміти

```powershell
pnpm exec wrangler tail
pnpm run telegram:webhook -- info
```

У Cloudflare перевіряйте Workers → Metrics/Logs і D1 → Metrics. Не публікуйте
сирі запити та секрети. Код webhook використовує загальний запис
`telegram_webhook_failed`, без тексту update і токена.

Після публікації версії з діагностикою завантажувач також пише:

- `source_refresh_succeeded`: дані успішно розібрані й збережені; `checkedAt`
  — час UTC у мілісекундах, `publishedDates` і `retainedDates` — кількості дат.
- `source_refresh_failed`: `stage`, `httpStatus`, `failureCount`, `nextAttemptAt`.
  Для `stage=parse` поле `parseReason` містить контрольовану причину з парсера.
  `stage=request` означає збій отримання відповіді, `http` — HTTP-помилку,
  `body` — читання або перевірку вмісту, `parse` — невідповідну структуру таблиці,
  `persist` — етап збереження, `timeout` — перевищення часу очікування.

`httpStatus=403` означає відмову сервера, але сам по собі не доводить постійний бан.
429 означає обмеження запитів; 5xx — відповідь про серверну помилку. 200 разом
зі `stage=parse` означає, що відповідь отримана, але таблицю не вдалося розібрати.
Сирі винятки, HTML, токени й особисті дані в ці записи не потрапляють.
Журнал починає збирати ці події лише після deploy нової версії; минулу помилку,
яку старий код не залогував, відновити з нового журналу неможливо.

Напис «Не вдалося оновити графік» означає останню невдалу спробу, а не доведений
бан чи недоступність сайту для всіх. Після відновлення відкрийте «Мій графік»
або `/schedule`: старе повідомлення у чаті автоматично не редагується.
Нові повідомлення надсилаються з вимкненим прев'ю посилань; саме посилання
на джерело залишається доступним.

- **Немає відповіді:** перевірте приватний чат, ID, секрет, webhook і міграції.
- **Немає графіка:** початкове очікування мовчить; `/schedule` показує кеш і час
  перевірки. У D1 `source_state` містить наступну спробу й стан джерела.
- **Сайт відповідає 429/503:** бот враховує `Retry-After` і збільшує паузи.
  Інші помилки теж запускають backoff. CAPTCHA та блокування не обходяться.
- **Telegram 429:** доставка відкладається за `retry_after`; блокування бота
  користувачем вимикає його автоматичні підписки.
- **Повтор після аварії:** можливий між прийняттям Telegram і записом
  підтвердження в D1. Гарантії exactly-once немає.

Перевірено за документацією 31.10.2026: Workers Free має 10 мс CPU на HTTP і
cron. D1 Free — 50 запитів на виклик Worker, 5 млн прочитаних і 100 тис.
записаних рядків на добу. Batch рахується одним запитом для ліміту виклику.
Очікування мережі не є CPU time. Частота cron сама по собі не доводить
відповідність лімітам: важливі розмір HTML, кількість підписників і доставок.

Починайте з одного власного ID. Після deploy виміряйте CPU звичайного cron,
завантаження HTML і циклу з доставкою, а також добові D1 read/write.
Хмарні вимірювання локально не виконані. За `exceededCpu` або
`Too many API requests` безкоштовний запуск не підтверджений: потрібна
оптимізація або свідомий вибір платного тарифу. Проєкт не підключає оплату.

## 9. Зупинка, оновлення й відновлення

Для особистої паузи: `/stop` → «Вимкнути все». Це не зупиняє перевірки для
інших користувачів. Щоб припинити запити до джерела й планування нових повідомлень,
задайте `triggers.crons: []` у `wrangler.jsonc` і повторіть deploy. Команди
продовжать працювати та можуть доставити вже поставлені в чергу повідомлення.
Для відновлення поверніть `* * * * *` і повторіть deploy.

Щоб окремо вимкнути приймання команд:

```powershell
pnpm run telegram:webhook -- delete
```

Це не зупиняє cron. Для повної паузи потрібні обидві дії; уже виконуваний
запит може завершитися. Якщо команди мають залишатися доступними, кожному
користувачу слід окремо вимкнути обидві автоматичні підписки через меню.
D1 не видаляйте:
там підписки, кеш і підтвердження надсилань. Перезапуск не скидає пам'ять
надісланих графіків; нагадування про початки, які минули, не наздоганяються.

Після зміни коду: тести → typecheck → lint → build → нові remote migrations,
якщо є → deploy. Перед ризиковими змінами зробіть експорт D1 за актуальною
документацією. Старі міграції не змінюйте.

Після ротації токена оновіть `.dev.vars`, `wrangler secret put BOT_TOKEN`,
повторіть `telegram:webhook set ...`, потім `info` і `/start`. Після зміни
`WEBHOOK_SECRET` оновіть локальне й хмарне значення та теж повторіть `set`:
інакше Telegram надсилатиме старий секрет і отримуватиме 401. Після зміни
адреси повторіть `set` для нової адреси. Не запускайте два Worker з окремими
базами для одного бота: у них не буде спільної дедуплікації.
