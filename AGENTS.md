# ROE Power Bot — правила розробки

## Призначення і поточний обсяг

Telegram-бот українською мовою для графіків Рівнеобленерго:
https://www.roe.vsei.ua/disconnections. Домовленості користувача збережені в
`CHAT_CONTEXT.md`. Поточний етап — початковий каркас; актуальний стан описує README.
Не видавати заплановані функції за реалізовані.

## Стек і навичка

- TypeScript, ESM, grammY, Cloudflare Workers; pnpm — єдиний менеджер пакетів.
- Vitest для тестів, Biome для форматування та lint, TypeScript для перевірки типів.
- Запитана користувачем навичка: `.agents/skills/telegram-bot-grammy/SKILL.md`.
  Читати її перед роботою з ботом; джерело —
  https://github.com/PBnicad/telegram-bot-grammy-skill (гілка `master`).
- Використовувати навичку як основу; перевіряти приклади за актуальною документацією.
  Не копіювати демонстраційні токени, BOT_INFO або database_id.
- Плановане сховище — Cloudflare D1. Додавати схему, міграції й Drizzle тоді,
  коли реалізовується збереження підписок, а не заради порожнього шару.
- Не додавати Express, NestJS, серверний polling або фонові нескінченні цикли
  до Workers. Для команд — webhook, для перевірок — Cron Triggers.

## Структура та якість коду

- Перед змінами читати актуальну реалізацію, конфігурацію та скрипти `package.json`.
- `src/index.ts` відповідає за HTTP; `src/bot.ts` — створення бота й реєстрацію
  обробників. Парсер, підписки та розсилку виділяти за відповідальністю під час реалізації.
- Тонкі обробники Telegram: перевірити вхід, викликати предметну логіку, відповісти.
- TypeScript `strict`; не послаблювати налаштування. Уникати `any`, небезпечних
  приведень типів, non-null assertions та `@ts-ignore`; використовувати `unknown`
  зі звуженням для недовірених даних.
- Явні типи на межах модулів, зрозумілі назви, короткі функції, guard clauses.
- Без зайвих абстракцій, універсальних репозиторіїв і залежностей без потреби.
- JavaScript у службових скриптах — ESM; для нетривіальних входів додавати JSDoc.
- Завжди обробляти Promise. Не приховувати помилки порожнім `catch`.
- Конфігурація Workers надходить через `env`, не через розсіяний `process.env`.
  Нові параметри документувати в README та файлі прикладу локальної конфігурації.

## Telegram і безпека

- Перевіряти шлях, HTTP-метод і `X-Telegram-Bot-Api-Secret-Token` до обробки update.
- BOT_TOKEN і WEBHOOK_SECRET — секрети Cloudflare; локально `.dev.vars`, який
  ігнорується Git. Не читати й не друкувати реальні секрети без необхідності.
- Не включати токен у callback_data, публічні URL або журнали. Telegram API URL
  містить токен: не логувати сирі винятки, що можуть містити цей URL.
- Не логувати весь update, тексти повідомлень або персональні дані користувачів.
  Для діагностики достатньо безпечних кодів помилок та update_id за потреби.
- Підписки початково підтримувати тільки у приватних чатах. Групи не мають
  змінювати особистий вибір; додавати їх підтримку лише як окрему вимогу.
- Callback_data вважати недовіреними: перевіряти допустиму дію, підчергу й
  користувача. Для callback query викликати `answerCallbackQuery` без зайвої затримки.
- Не вставляти зовнішній текст у HTML/Markdown без escaping; за замовчуванням
  використовувати звичайний текст. Ділити довгі повідомлення на межах записів.
- `/stop` має припиняти розсилку. Не відправляти користувачу нічого до його згоди
  через взаємодію з ботом. Зберігати лише дані, необхідні для підписки.
- Не використовувати in-memory sessions або глобальні змінні як постійне сховище.
- Враховувати повторну доставку update й паралельні виклики. Записи робити
  ідемпотентними; для розсилок потрібний контроль одночасної обробки в сховищі.
- Не поглинати критичну помилку webhook і не повертати успіх при втраті update.
- Для Telegram 429 враховувати `retry_after`; для блокування бота користувачем
  припиняти спроби розсилки. Не робити необмежені retry у межах одного запиту.

## Правила графіків і розсилки

- Одна спільна перевірка джерела раз на 5 хвилин, а не запит на кожного підписника.
  Ручні команди читають збережений графік, а не перевантажують джерело.
- Вибір: підчерги 1.1–6.2 або всі підчерги. Вибір зберігати для кожного користувача.
  `/all` — одноразовий перегляд без зміни вибору.
- Немає графіка / «Очікується» — немає автоматичного повідомлення.
- Сповіщати після появи графіка, зміни годин вибраної підчерги або появи нової дати.
  Не реагувати на зміну інших підчерг чи лише часу «Оновлено».
- Порівнювати нормалізовані дату та предметний вміст, а не весь HTML.
  Стан останнього успішного надсилання зберігати між перезапусками.
- Не позначати повідомлення надісланим до підтвердження Telegram. Врахувати,
  що збій між надсиланням і записом стану може дати повтор; не обіцяти exactly-once.
- Завантаження має мати timeout та обмеження розміру. Валідувати структуру,
  відповідність заголовків підчергам і дати; неоднозначні дані не розсилати.
- Помилка парсингу або мережі не означає скасування графіка. Не затирати останні
  коректні дані; під час ручного перегляду показувати їхню давність.
- Для 429/503 враховувати Retry-After і збільшувати паузу після помилок.
  Не обходити CAPTCHA або блокування доступу.
- Час джерела трактувати в `Europe/Kyiv`; не покладатися на часовий пояс сервера.
  Автоматичні повідомлення не повинні повторно розсилати минулі дати.

## Перевірка і робочий процес

- Виконувати актуальні скрипти: `pnpm run typecheck`, `pnpm run lint`,
  `pnpm test`, `pnpm run build`. Після появи lockfile використовувати
  `pnpm install --frozen-lockfile` для відтворюваного встановлення.
- Тести перевіряють видиму поведінку. Зовнішні HTTP-запити замінювати на межі;
  у тестах не звертатися до реального Telegram чи сайту і не використовувати токени.
- Обов'язкові сценарії під час відповідної реалізації: неправильний secret,
  команди у групі, невалідний callback, «Очікується», кілька дат, зміна однієї
  підчерги, повтор update, незмінний графік, помилка джерела й помилка надсилання.
- Парсер перевіряти на збережених HTML-фікстурах реальної структури без персональних даних.
- Перед завершенням вказати виконані перевірки, обмеження й запропонувати
  Conventional Commit. Не стверджувати успішність невиконаних перевірок.
- Не комітити, не пушити, не створювати PR і не деплоїти без запиту користувача.
- Не створювати платні ресурси, не змінювати webhook реального бота й не надсилати
  повідомлення стороннім користувачам як частину локальної перевірки.
